# Architecture

The Spine Clinic client is a Flutter application backed by Supabase (PostgreSQL,
Auth, Storage). It follows **feature-first Clean Architecture** with unidirectional
dependencies: presentation → domain → data → network → Supabase. This document
describes the codebase as it is; the prescriptive engineering rules live in
[AGENTS.md](../AGENTS.md).

## Project Layout

```text
lib/
├── main.dart                 # Startup: SharedPreferences, Supabase, Sentry, ProviderScope
├── core/
│   ├── constants/            # AppTheme, AppColors/AppPalette, AppSizes, AppStrings, AppTextStyles
│   ├── errors/               # Result<T>, AppException hierarchy
│   ├── network/              # SupabaseService, GoRouter (routes, guards, navigation)
│   └── utils/                # Formatters, local settings providers, file helpers
├── shared/
│   └── widgets/              # ~57 reusable components (AppShell, AppButton, ErrorView, …)
└── features/
    ├── auth/                 # Splash, login, register, profiles, doctor history
    ├── patient/              # Search/list, patient dossier (tabs), documents, due collection
    ├── appointment/          # Schedule, booking workboard, appointments detail, doctor replacement
    ├── medical_records/      # Visit details, visit notes, patient notes
    ├── payments/             # Record payment (amount / package / reason)
    ├── staff/                # Staff directory, applications, staff form
    └── admin/                # Admin hub, analytics, reports, branch switching
```

Each feature folder is layered `data/` (repository implementations, DTOs) →
`domain/` (Freezed models, repository interfaces) → `presentation/` (screens,
notifiers, providers). One known deviation: `staff/` has no `domain/` layer yet
(tracked in AGENTS.md technical debt).

## Data Flow Contract

The intended feature flow is:

```text
Widget (user action)
  → Riverpod Notifier (holds state, orchestrates)
    → Repository interface (domain layer contract)
      → Repository implementation (data layer)
        → SupabaseService (core/network, error normalization)
          → Supabase (RLS + triggers enforce integrity)
```

Widgets contain **zero** database calls. Repositories return domain models, never
raw row maps.

## Error Model

- [`core/errors/result.dart`](../lib/core/errors/result.dart) defines a sealed `Result<T>` (`Success` / `Failure`)
  with `when`, `map`, `flatMap`, and `dataOrNull`. Every async repository method
  returns `Result<T>` by contract; this does not rule out unexpected runtime errors.
- [`core/errors/app_exception.dart`](../lib/core/errors/app_exception.dart) defines the failure taxonomy (`AuthException`,
  `DatabaseException` with Postgres-code mapping including RLS `42501`,
  `NetworkException`, `NotFoundException`, `StorageException`, `UnknownException`).
- `SupabaseService` wraps the Supabase client and normalizes every Supabase
  error into the matching `AppException` before it reaches a repository.
- Screens render four mandatory states — loading, error, empty, data — usually
  via shared `ErrorView` / `EmptyState` / skeleton widgets.

## State Management

Riverpod 3 with code generation:

- Providers are declared with `@riverpod` and generated by `riverpod_generator`
  (run `dart run build_runner build --delete-conflicting-outputs` after edits).
- Shared, cross-screen, and repository-backed state lives in Notifiers /
  AsyncNotifiers (e.g. `AuthCurrentUser`, `TodayAppointments`, `BookingWorkboard`,
  `DoctorScheduleNotifier`, `AnalyticsFilterNotifier`).
- State classes mutate exclusively through `copyWith` so unspecified fields keep
  their value (hand-written `copyWith` or Freezed).
- Notifiers that depend on async providers `ref.watch` them inside `build()` and
  start loading via `Future.microtask` — never `ref.read(...).value`, which
  silently returns null before the dependency resolves.
- Interactive search and filter inputs debounce at **300 ms** before hitting
  repositories.
- `setState` is reserved for widget-local concerns (submission flags, password
  visibility, in-sheet filter selections, expand/collapse).

## Navigation & Role Guards

Routing is declarative GoRouter (`core/network/`):

- `router_routes.dart` declares the route names; `router_guards.dart` applies
  authentication and role redirects.
- Role-based home: doctor → `/schedule`, receptionist → `/allAppointments`,
  super admin → `/reports`. `/admin*` routes are admin-only.
- Navigation chrome comes from `shared/widgets` (`AppShell`, `AppNavBar`,
  `AppNavRail`, `NavTabs`), which renders the tab set for the current role:
  doctor (My Schedule / My Patients / Profile), receptionist (Appointments /
  Patients / Profile), super admin (Analytics / Appointments / Patients / Admin).

Roles come from the database enum `user_role` (`super_admin`, `receptionist`,
`doctor`) mirrored by the Dart `UserRole` enum in `features/auth/domain/`.
There is no patient login — patients are data, not users.

## Design System

- Material 3 with light/dark themes built in
  [`app_theme.dart`](../lib/core/constants/app_theme.dart)
  (+ `app_theme_components.dart`) from the palettes in `app_colors.dart`,
  `app_palette.dart`, and `clinic_colors.dart`. Palettes are **seed values only** —
  widgets read `Theme.of(context).colorScheme` or the registered `ClinicColors`
  theme extension.
- Spacing/sizing map to `AppSizes`; typography to `AppTextStyles`; user-visible
  strings to `AppStrings` (English-only constants; `intl` handles date/number
  formatting). There is no ARB/l10n pipeline.
- Bundled fonts: Inter and Plus Jakarta Sans variable fonts; icons via
  `flutter_lucide`; motion via `flutter_animate`.
- The current theme uses clinical blue; `AppTextStyles` uses Plus Jakarta Sans.
  Existing pill buttons and rounded cards describe current components, not a
  required layout for every future screen. [DESIGN.md](../DESIGN.md) contains
  design guidance; [the UI overhaul plan](ui-overhaul.md) tracks proposed work.

## Startup Sequence

[`main.dart`](../lib/main.dart):

1. `SharedPreferences.getInstance()`.2. Resolve Supabase credentials: `--dart-define` flags → bundled `.env` asset →
   compiled-in defaults.
3. `Supabase.initialize(url, anonKey)` via `SupabaseService`.
4. `runApp(ProviderScope(...))` with the preferences override; root widget is
   `MaterialApp.router` wired to `routerProvider`, with light/dark `AppTheme`
   and a `themeModeControllerProvider` for system/light/dark switching.

## Platform Targets

All six platform folders exist (Android, iOS, web, Windows, Linux, macOS).
Both **desktop and mobile are primary usage contexts** (see
[PRODUCT.md](../PRODUCT.md)). `AppShell` already switches between bottom
navigation and a navigation rail, but this does not establish that every screen
adapts its content well. The overhaul targets content and interaction structure
as well as navigation. Web is the primary demo target (Firebase Hosting), and
iOS IPAs build through GitHub
Actions ([`.github/workflows/build_ios.yml`](../.github/workflows/build_ios.yml)).


## Review changes (2026-09-06)

Patient and appointment edits now call atomic database RPCs, including optional
assignment changes. Balance-only edits have a separate repository method.
Mutation controllers use generated keepAlive providers. Appointment detail
stops retrying permanent application errors. Document repositories follow
session changes to avoid reusing another account's in-memory cache.

The custom Sentry reporter sanitizes database failures and omits staff names;
automatic event/breadcrumb privacy still needs staging verification. Registration
is already a two-step form. Current file objects use R2 through a Supabase edge
function, with PostgreSQL metadata as the source of truth.

These changes are local and require coordinated backend/client deployment.
See [review results](pre-delivery-review-results.md) for known remaining issues.

## Browser review fixes (2026-09-06)

Authentication redirects preserve protected deep links through the splash screen
and re-check role access before restoring them. Payment JSON emits `recorded_at`
in UTC with an explicit `Z`; views continue converting timestamps to local time.
Doctor selection callbacks receive list copies so form saving cannot clear the
field through an aliased parent list. Appointment status actions invalidate the
patient detail cache as well as appointment lists, refreshing package balances.
